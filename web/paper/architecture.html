System architecture

Design principle: two integrity layers

Signatures and watermarks fail in opposite places, so the design uses both:

LayerProvesSurvives re-encoding?
Cryptographic signature over content hashesExact integrity, device identity, capture timeNo — any transcode invalidates it, by design
Robust invisible watermark (VideoSeal)Pointer to the capture (random 128-bit capture id) — the key that finds the verified original for comparisonYes — measured ≥94.9% bit accuracy under aggressive transcodes

Capture & signing pipeline

  1. Device setup — no account: an ECDSA P-256 key pair is generated inside StrongBox (dedicated secure element; TEE fallback on devices without it — the level is recorded in every proof). Android Key Attestation produces an X.509 chain binding the key to hardware; the chain travels inside every proof. The app picks a random device UUID and a display name — the identity a future cloud registration will bind to this key.
  2. Capture: photo or video from the app, saved to the gallery. Each capture gets a fresh random 128-bit capture id.
  3. Watermarking — on the device: the capture id, protected by BCH error correction, is embedded into the pixels by the on-device VideoSeal pipeline (ONNX) — same payload for photos and video. Fully offline; media never leaves the phone.
  4. Signing: the SHA-256 of the watermarked bytes is signed in the secure element (SHA256withECDSA). The private key never exists in application memory.
  5. Proof-in-file: the proof (capture id, device id, timestamps, public key, attestation chain, signature) is appended to the file itself as a trailer that is also a valid MP4 free box, so players and JPEG decoders ignore it. There is no server and nothing to sync — the file carries its own proof wherever it goes.

Proof trailer & signature convention

trailer   = [4B box size]["free"][proof JSON][4B json length]["TCPROOF1"]
canonical = file bytes without the trailer
H         = SHA-256(canonical)               // 32 bytes
sig       = ECDSA-P256( SHA-256(H) )         // Android SHA256withECDSA over H

The verifier (a static page — WebCrypto, no backend) strips the trailer, recomputes H and checks sig against the public key carried in the proof; it also checks that the attestation leaf certificate certifies that same key (validation up to Google's attestation root is on the roadmap). The proof is a claim, the signature is the evidence, and it is re-checked from scratch on every verification — by your browser, not by a service you must trust.

The algorithms

Every layer is built on published, battle-tested primitives — nothing bespoke guards anything important:

  • Neural watermark — VideoSeal (Meta AI): an encoder/decoder network pair trained adversarially against simulated compression, resizing and cropping. The encoder learns where in the image a 256-bit message can hide below visual threshold yet survive platform processing; the decoder returns per-bit confidence ("soft bits") that can be averaged across video frames, so evidence accumulates over time.
  • Error correction — BCH(255,131): the algebraic code family that keeps QR codes and deep-space telemetry readable. It guarantees exact recovery of the capture id with up to 18 corrupted bits — and beyond that it fails clean: an id is either exactly right or explicitly absent, never silently wrong (0 miscorrections in 31,000 adversarial trials).
  • Signature — ECDSA P-256 on a key generated inside the phone's secure element and physically unable to leave it, with Android Key Attestation binding the key to hardware in every proof.

Watermark payload encoding

The watermark carries a 256-bit message decoded from the pixels. Robustness comes from structure, not secrecy. The current format (v3) carries a random capture id; the verifier tries it first (its BCH check has a ~2−124 false-accept rate, so a hit is authoritative), then falls back to the legacy v1 format:

v3 — photos and video (app ≥ 1.2.0): capture id

The id carries no meaning by itself — it is a random UUID drawn at capture. Its job is to be a lookup key: given any surviving copy, the verifier recovers the id and resolves it to the record of the original capture (the verified originals on file today, a cloud registry in the full design). 128 random bits make guessing or colliding ids a non-issue.

v1 — captures before 1.2.0: device pointer

Extraction averages the decoded signal across sampled frames, soft-combines the eight copies of each bit, and accepts the result only if the CRC validates and signal agreement exceeds a threshold. Measured end-to-end (both formats): full payload recovery after real YouTube and WhatsApp round-trips and 720p/2Mbps re-encodes (data).

Bitstream signatures for video (next iteration)

Whole-file signing is the current baseline. The validated upgrade path embeds a rolling signature per GOP (group of pictures) directly in the H.264/H.265 bitstream as SEI NAL units in the ONVIF Media Signing format: each GOP's hash chains the previous one, proving continuous, ordered, real-time capture, and making any cut or splice detectable at GOP granularity. Our device tests confirmed these SEI units pass through the hardware encoder and MP4 muxer untouched on consumer hardware (60/60 preserved, Qualcomm c2.qti.avc.encoder).

Verification — fully client-side

The verifier is a static web page: nothing is uploaded, ever. Given any file it resolves in order — each level is weaker than the previous and the UI says so explicitly:

  1. Proof trailer present → strip, hash the canonical bytes, verify the signature with WebCrypto against the key in the proof (attestation leaf cross-checked) → Verified (original). Works offline; survives any byte-exact transfer (email, Drive, file transfer).
  2. No trailer (platforms strip it — but they also change the bytes, so the signature was lost either way) → watermark extraction in the browser (int8 ONNX detector, ~34 MB, WASM). Photos are scanned directly; videos are scanned by sampling 24 frames and averaging the decoded signal. The recovered capture id is looked up in the verified originals on file: a hit shows the copy side by side with the verified original; a miss yields Origin traced only.

A command-line verifier (/verify.mjs) runs the same checks for scripting and batch workflows.

Verified originals: comparing the copy with the capture

The mark alone identifies origin, never integrity: it survives whatever preserves most of the pixels — platform re-encoding, moderate crops, screenshots — which by the same token includes edits that keep most of the original. Instead of trying to judge integrity from the surviving signal, the design resolves the capture id to the original file, cryptographically verified at the source, and puts it next to the copy: any depicted difference is an edit, and a human sees it immediately. In the full design the app registers the device and uploads each sealed original to a cloud registry at capture time; today, with no server, a static samples file holds a handful of demo captures so the flow can be tried end to end. One honest caveat: an attacker with the open embedder can stamp any content with any id — a mark-only match is an origin claim, and the comparison is evidence for human judgement. Cryptographic proof remains exclusive to the signed trailer.

The binding constraint on recovery is surviving content area, not the transform chain. Measured on the production photo pipeline (simulation in spikes/sim_screenshot.py and spikes/spike_strength_sweep.py): a 4080px capture re-encoded by an Instagram-class pipeline (1080px, quality 60), screenshotted and manually cropped still decodes cleanly at the production embed strength (×1.2, PSNR ≈45 dB); below roughly half of the original area, decoding fails at any embed strength — the verifier then reports No proof found, deliberately indistinguishable from "never captured with TrustCam", because claiming anything from an unreadable signal would be guessing.

Trust model and standards alignment

The design maps onto C2PA concepts (hard binding = content hash + signature, carried in the file exactly like a C2PA manifest; soft binding = watermark) and is built to become C2PA-conformant: the trailer can be re-expressed as a C2PA manifest, and the device keys/attestation flow matches the requirements of C2PA Conformance Level 2 (hardware-backed keys). With no server anywhere, capture time is device-claimed only; RFC 3161 timestamp tokens (fetched at capture when online) are the planned upgrade.
